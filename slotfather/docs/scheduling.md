# Scheduling

`grant()` runs in every client that looks at the queue (each waiting request, every few seconds, and each release), and it starts the waiting requests `plan()` picks:

1. Waiters are taken in arrival order, moved by their priority and its ageing (see Priority below), with the requests that came after the head behind it (rule 3); each that fits starts.
2. A waiting request that does not fit lets later requests that fit start first for `SLOTFATHER_OVERTAKE_WINDOW` seconds after it queued (600), as before.
3. The first waiting request past its window that does not fit is the **head**. Its start is **reserved**: the moment the held leases' expected ends free enough slots for it, and never later than any earlier look reserved it (the entry keeps it as `reserved`; each look takes the earlier of that and what it projects now). A later request that fits starts before it only if three times (*safety*) its expected run ends by that reserved start, or if it takes only spare slots: those the head will not need at its projected start even if the leases expected to run on past it are the largest ones (EASY backfill, made independent of which lease ends first). *Later* means it came after the head, whatever its class: once a waiter is the head, an interactive request that came after it is not ranked ahead of it any more, it passes only as backfill. Short work keeps flowing beside a waiting all-slot request, and nothing that came after the head can move its start later; only the leases it waited for, running on past their estimates, and work that passed it running more than *safety* times its estimate can. A request that came before the head and moves ahead of it in the class order (ageing, `reprioritize`) becomes the head instead, and the reservation is its. With a *limit* (`--limit S`, off since the reservation: 0), from the moment the head has waited it nothing passes at all, as before.
4. A waiting request whose client gives up first is no head (`run --wait`, the library's `acquire(wait=...)`, writes the moment on its entry as `until`): when even the held leases' expected ends free its slots only after it gives up, counting the *overrun* of a lease already past its expected run as the head's reservation does, it would leave without running, so the next waiting request past its window that does not fit is the head instead and requests that fit pass it. This holds past its limit too (#5): nothing passes a head from then on, but the leases it waits for still run on, and on 2026-11-10 three `-n all --wait 3300` reruns were the head for the last ten minutes of their wait behind checks an hour past their estimates, then left without running beside idle slots. It keeps its head while any held lease's run is unknown (it may end any moment; counting the fallback would give the head up on a guess and make its give-up come true) or slots are held in an earlier queue; it still starts if its slots come free before it gives up. A lease back in the queue after a yield keeps its head whatever its first wait said. Older clients read past `until` and hold back for such a waiting request as before.
5. A **batch** request never holds back a waiting normal or interactive request (#5) until it has aged to normal (*aging_batch*, 30 minutes), whatever its slot count, also when it is back in the queue after a yield. While such a request waits, the batch one is no head, and a batch request for the **whole machine** (`-n all`, or a count of at least the capacity) does not start either, since it would shut that work out for its whole run. Once no normal or interactive request waits, it is the head as before: it holds later batch work back, the held leases drain, and it starts by its limit plus the overrun of what passed it. Each look decides again, so the head comes and goes with the other work. On 2026-11-10 a batch, yieldable `-n all` measurement ranked at its arrival plus 1800 s became the head in front of normal lane checks that came later, and past its limit kept five slots idle behind one running check. Normal and interactive requests keep the head as before, also when they are yieldable.

Expected runs come from `history.jsonl` (its last megabyte, read only when a request fits behind a head and kept in `estimates.json` beside it until the history changes, so other processes, releases and `available` read the small file; a file another version wrote is worked out again): the median of the last 20 released runs of the closest earlier kind of request, trying in turn the same label and command kind (`stats`' kind: program and first argument, with a runner's `run` target, a shell's `-c` command and no `env VAR=…`), the same label family (the label up to its ticket or agent id: `lane`, `post-merge`) and kind, that family with a check list of about the same size (`verify.sh --checks` of 128 to 255 checks), the kind under any label, about that size under any label, the same label, and the same family. Reaped leases and requests that gave up are left out: a reaped lease's time runs to whenever a look noticed its holder had died (an orphan of a hung CI job kept its slot for 2800 s), and one that gave up never ran. This leans the estimates short for a kind whose runs are often killed after real work (a CI job cancelled or timed out late in its run): only its runs that finished count. A request like nothing before counts as running the *fallback* (3600 s), so with the default limit it passes a head only into spare slots. A held lease past its expected run is expected to run on for the *overrun* share (half) of what it has run so far, because a run that overran its kind tends to be a long one.

`available` and `advise` answer for a request of unknown run (the fallback) unless given the command: `slotfather available --label L -- COMMAND...`, `slotfather advise [--max N] --label L -- COMMAND...`; `advise` reports the run it expected as `run_estimate` (`null`: unknown).

**Settings.** `slotfather order` shows the order and its numbers; `slotfather order backfill|window`, `--safety X` (at least 1), `--limit S` (0, the default: no limit), `--fallback S`, `--overrun X`, the classes' `--interactive S`, `--batch S` and `--yield-after S`, the ageing steps `--aging-batch S` and `--aging-normal S` and the long-wait signal's `--warn-wait S` (see Ageing below), and the idle thresholds `--idle-cpu C` and `--idle-after S` (see below); a time takes seconds or a unit, `90`, `90s`, `30m`, `1.5h`, save them for every client in `order.json` beside the queue, like `slots` saves capacity, and `slotfather order reset` restores the defaults. They take effect at the next look at the queue, also while it is busy. Every client's look grants for the whole queue, so a client's environment can only tighten them: `SLOTFATHER_QUEUE=window`, or a higher `SLOTFATHER_BACKFILL_SAFETY` or `_FALLBACK`, a lower `_OVERRUN` or a lower nonzero `_LIMIT`, a lower `SLOTFATHER_PRIORITY_INTERACTIVE` or `_BATCH` (classes move requests less), a higher `SLOTFATHER_YIELD_AFTER` or `0` (nobody is asked), a higher `SLOTFATHER_AGING_BATCH` or `_AGING_NORMAL` or `0` (classes move requests less); looser values are ignored. `SLOTFATHER_WARN_WAIT` decides nothing for other clients and sets this client's own long-wait signal either way. A saved file that cannot be read gives the window order. The class, ageing and warn knobs are written to `order.json` only when they differ from their defaults: a slotfather before them refuses a file with keys it does not know and falls back to the window order, and `slotfather order` says so when it saves one.

**When an estimate is wrong.** A request that runs longer than expected delays the head by the difference. The reservation bounds it: none passes that is expected to end after the reserved start, which never moves later, so beyond the leases it waited for, the head waits only for the overrun of what passed it, at least *safety* times its estimate. Before the reservation the head's start moved on with the held leases' overrun, more work was let through against the later start, and only the limit (then 2700 s) stopped it, by letting nothing through at all. An overestimate only keeps a request behind the head, as the window order did. The replays below with estimates halved, doubled and scattered (each one off by a random factor, e^N(0,1)) keep the longest wait of large requests at the current order's.

**Mixed versions.** A slotfather before ageing reads past `reserved`, `aged`, `reprioritized` and `reprioritized_at` on entries, and keeps its own head limit (2700 s): `order.json` holds `limit` only when it is not 0, so an older client reading a file without it keeps that bound, the only one it has. A file saved before this version holds `"limit": 2700` and keeps it until `slotfather order --limit 0`. Every client keeps the head's reservation by the shared settings, whatever its environment tightens (`SLOTFATHER_QUEUE=window`, a longer ageing step), so such a client neither drops nor resets it; a lease that yields drops any reservation an older client granted it with. A lease back in the queue after a yield keeps its pin just behind the waiter it yielded to, also when that waiter came before the head; it then starts ahead of the head with the rest of its run, as before. its looks rank by the class a request asked (or the one `reprioritize` set), without ageing or reservations, so until every client is updated a look of either version may start what its own order allows. Queue entries, `history.jsonl` and every output (`status`, `available`, `advise`, `slots`, `history`, the lease variables and nesting) are unchanged, so old and new clients share one queue. An older client grants by its own order whenever it looks, so until every client is updated the queue admits what either order allows: a new client's look starts a short request an old one would hold back, and an old client's look keeps today's behaviour for what the new order would refuse. Straylight's vendored `tools/slotfather` predates the history, so its runs are not in the estimates until it uses this one.

**Alternative current policy.** `slotfather order window` uses arrival order and the
overtaking window without priority offsets or yield requests. `--yield-after 0`
disables cooperative yield requests while keeping the backfill policy.

### Priority

`run --priority interactive|normal|batch` (library: `acquire(..., priority="interactive")`)
sets the request's priority. **interactive** is work a person or agent is waiting
on, such as a focused test. **batch** is unattended work or measurements;
`-n all` does not set priority by itself. Omitted priority is **normal**.
Priority and ticket use their own named options, not metadata.

The priority moves where a waiting request stands in the order, by a fixed offset: an interactive waiting request queues as if it came *interactive* seconds (1800) earlier, a batch one as if it came *batch* seconds (1800) later. Ageing (below) moves a waiting request up a class as it waits, so a batch request is served as normal after 30 minutes and as interactive after 90, each time at its own arrival. The window order (`slotfather order window`) has no classes.

Apart from rule 5 above, priority changes only the order in which `plan()` takes the waiting requests; the window, the head and its reservation then work as before on that order, and the window and the limit count from when a request really queued. The head is the first waiting request in priority order that is past its window and does not fit; from then on the requests that came after it are behind it whatever their class (rule 3), so only requests that came before it can rank ahead of it, and they do only by ageing or `reprioritize`. The bound: a head starts once the leases held when it became the head end, plus the overrun of what passed it; a batch request becomes a possible head once it has aged to normal (rule 5: until then, while normal or interactive requests keep coming and waiting, it is no head, and before ageing a batch `-n all` measurement waited until they stopped, six hours on 2026-11-11). The replay tests have these traces. An interactive request that does not fit becomes the head in its turn and gets the head's reservation. A lease that yielded and does not fit becomes a head too; its limit counts from when it yielded.

### Ageing

A waiting request moves up one class after waiting *aging_batch* seconds as batch (1800: it is then served as normal) and *aging_normal* more as normal (3600: then as interactive); a normal request becomes interactive after *aging_normal*. `0` stops it at that class. An aged request keeps its arrival: it ranks as a request of its new class that came when it came, so it is ahead of every later request of that class, and a batch request reaches the interactive class after 90 minutes at most, from when it queued. Ageing moves a request only up, and only while it waits: a held lease keeps its class, and one back in the queue after a yield ages from when it yielded. Everything that reads a class reads the aged one: the order, rule 5 (an aged batch request is normal and no longer defers), and yield requests (a request aged to interactive asks). `grant()` writes the class a request was granted in as `aged` on its entry; the history line keeps `priority`, the class asked, and adds `aged`.

`slotfather reprioritize PID|LABEL interactive|normal|batch` moves one request (a label must name exactly one, or one waiting request) to another class without losing its place: its `since` stays, so it ranks as a request of the new class that came when it came; its ageing starts again from the change (`reprioritized_at` on the entry), so a request moved down stays there for the new class's steps. Only its owner may (the uid of its holder); the entry keeps the class it asked first as `reprioritized`, queue.log records `reprioritized LABEL (pid N) from A to B` (EVENTS shows it), the history line adds `reprioritized`, and the queue grants at once. Queueing the request again instead gives it a new arrival: on 2026-11-11 the Safari run lost six hours of seniority that way, twice.

**Long waits.** A request that has waited *warn_wait* seconds (1800; `0`: never) says so on its client's stderr and again every 15 minutes: `slot: LABEL (pid N, CLASS) waiting 45m00s behind 3 earlier requests and 8 running leases: est. start 18:40; reprioritize with: slotfather reprioritize N interactive` (no hint once it is interactive). Each such line also goes to queue.log as `waiting long: ...`, which EVENTS shows, and `status` flags the request with `long-wait=45m00s` (`status --json`: `long_wait`, `waited`).

**Expected starts.** `status` gives every waiting request `est-start=` (UTC), and `status --json` `est_start`: when the queue is expected to start it if nothing more comes. `schedule.forecast()` plays the queue forward with the same `plan()`: each held lease ends at its expected end (overrun counted), each grant runs its expected run, the head keeps its reservation, and requests age as they wait; memory, yields and give-ups are left out. `?` (`null`) where it cannot tell: slots held in an earlier queue. `status` also shows the class a request is served in (`priority=`, `aged-from=`, `reprioritized-from=`; JSON `effective_priority`, `aged`, `reprioritized`) and marks the head with its reserved start (`head reserved=`; JSON `head`, `reserved`).

#### Example

Eight slots; seven held by lane checks expected to end between 18:05 and 18:20, one free. At 17:00 a Safari profile run asks for `-n all` as batch, and interactive tests keep coming, one a minute: half of them run 20 s, half 5 minutes.

- 17:00 to 17:30: batch, it lets the tests go first (rule 5); each starts in the free slot or as a check ends.
- 17:30: it has aged to normal, ranks at its arrival, 17:00, ahead of every test that came after it, and is past its window: it is the head. The checks then running are expected to end by 17:34, its reserved start.
- 17:30 to 17:34: a 20 s test passes (3 × 20 s ends before 17:34); a 5-minute test waits behind it (3 × 5 min does not). A test that comes now is no longer ranked ahead of it, though interactive.
- One check runs on to 17:38: the reservation stays 17:34, so from 17:34 on nothing passes, and the run starts at 17:38, when the check ends. Before ageing and reservations it started only once the tests stopped coming.

### Idle leases

A running lease is **idle** (#12) when its command's process tree has used less than `idle_cpu` cores (0.1 by default) for `idle_after` seconds (300) or more, with no process starting or ending in between: a build that spawns short compiler processes is never idle, and neither is a short pause for the network, a disk or a browser. The holder measures its own tree each time it samples it (the same samples as the history's usage), counting each process's own CPU and that of the children it reaped, so workers started and gone between two samples count, and records since when it has been low in `<entry>.idle` beside its queue entry, with an expiry by its own sampling interval; a lower `idle_cpu` than a run was built under starts that run again; every reader applies `idle_after` to that record, so the dashboard, `status` (`idle=23m`), `status --json` (`idle_since`) and the yield ask share one definition. A record past its expiry (three of its holder's longest sampling intervals, at least 30 s) says nothing, and older holders write none: their leases are never idle. While a request waits that the slots of an idle lease would start, a look asks that lease to yield through the same yield request as polite preemption, when it is `yieldable` and was asked fewer than YIELDS_MAX times; a lease that cannot yield is only marked. The scheduler never stops or kills an owner. Holders and readers decide idle by the saved settings alone, as every look decides yield requests, so that clients agree; `SLOTFATHER_IDLE_CPU` (lower) and `SLOTFATHER_IDLE_AFTER` (higher) only change what this client's `slotfather order` and Settings report as effective. Like the class knobs, they are written to `order.json` only when they differ from their defaults.

### Polite preemption

A holder that opted in (`run --yieldable`, `acquire(..., yieldable=True)`) can be asked to give its slots back for a while; it is never stopped, killed or signalled, and a holder that did not opt in is never asked. An **interactive** waiting request asks when it has waited *yield_after* seconds (120), does not fit, and by the held leases' expected ends would not get its slots within another *yield_after*. It asks only yieldable holders of a lower priority that have held their slots *yield_after* seconds since their last grant and have yielded fewer than two times; only as many as it needs (first those already asked, then batch before normal, then the one expected to run longest); and only when the queue would then start it, with the asked holders back among the waiting requests. Every look decides again: a request no longer needed (the waiting request started or left) is withdrawn.

The waiting request's own client may ask later or never (`SLOTFATHER_YIELD_AFTER`); that rides on its queue entry as `yield_after`, and every client's look decides yield requests by the saved settings and those entries alone, so clients with different environments do not write and withdraw each other's requests. A holder asked to yield checks once more that the waiting request would then start, and keeps its slots when it would not. The yield request is a file beside the holder's queue entry, `<entry>.yield`, whose path the lease's command gets in `SLOTFATHER_YIELD`; it holds `{"by", "label", "priority", "count", "at"}` of the waiting request that asked. `slotfather yield` from inside the lease (the library's `lease.yield_slots()`) yields if asked and the waiting request still waits: the lease goes back to the queue (the same entry and holder, state `waiting`) just behind that waiting request, pinned there whatever its priority (it is half done and holds its memory), the queue grants at once so the waiting request starts, and the command returns when the lease is granted again with its slots. Without a yield request it returns at once, saying `no yield requested`; it exits 0 either way. A nested `slotfather run` under a yielded lease waits until the lease is back. `status` shows `yieldable`, `asked-to-yield-for=LABEL` and `yielded=N`; `status --json` adds `priority`, `yieldable`, `yields`, `yield_asked` (the request or `null`) and `position` (a waiting request's place in the order the queue serves); the dashboard's details panel shows the request; `queue.log` records asks, withdrawals and yields. The history line of a lease that yielded carries `yields` and `yielded` (seconds back in the queue); its wait and run count from its first grant, and `stats` leaves the yielded time out of cores per slot.

#### What a client implements to be preemptible

Straylight's `tools/verify.py` and `tools/heavy.py` and Sid-Kit's `scripts/heavy.sh` and `scripts/verify.mjs` are the intended clients; they are not changed here.

1. **Opt in when taking the lease**: `slotfather run --yieldable --priority batch ... -- COMMAND` (Sid-Kit's `heavy.sh`), or, for a client that holds its lease in-process (Straylight's `verify.py` through `tools/slot_lease.py`), `acquire(count, label, command, yieldable=True, priority="batch", meta={...})`.
2. **Look for a request between steps**, whenever a step ends and none of the lease's own work runs: Straylight between checks, Sid-Kit between `verify.mjs` steps. The look is one `stat`: `[ -e "$SLOTFATHER_YIELD" ]` in a shell, `os.path.exists(os.environ.get("SLOTFATHER_YIELD", ""))` in Python, `lease.yield_requested()` in-process. With parallel jobs (`--jobs N`), stop starting new steps once a request is seen and let the running ones finish first.
3. **Yield**: run `slotfather yield` (in-process `lease.yield_slots()`); it blocks while the lease is back in the queue. Then go on with the next step, with the same slots. Nothing has to be undone: a yield happens between steps. **If `slotfather yield` exits non-zero** (in-process: raises `SlotError`), the lease is gone (its holder was reaped, the queue removed) or the command did not run inside it: stop, and do not run further steps unleased. Exit 0 means the lease is held, whether or not it yielded.
4. **Never** yield in the middle of a step or a measurement (a measurement does not opt in), never kill or signal a process to make room, and do not start new work under the lease while yielding.

A client may ignore a request: the waiting request then waits as it would have, and the request is withdrawn once it is no longer needed.

**Mixed versions.** A slotfather before classes (`3e3a621` and earlier, Straylight's vendored copy) ignores them and the requests: its looks grant in arrival order, so until every client runs this version a waiting request may start as either order allows. It lists a yielded lease as a waiting request and may grant it again before the waiting request it yielded to; `slotfather yield` then returns as usual. Since the yield itself grants at once, the waiting request normally starts before an older client looks.
